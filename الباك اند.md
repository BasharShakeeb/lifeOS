## Database Requirements

Before implementing any endpoint:

- Read the existing Supabase schema.
- Follow the exact table names.
- Follow the exact column names.
- Follow the exact data types.
- Follow all foreign key relationships.
- Respect constraints and indexes.
- Use the existing enums.
- Do not rename fields.
- Do not create duplicate models.
- Do not assume missing fields.

The backend must be fully synchronized with the Supabase database structure.

---

## Architecture

Use the same architecture already implemented for **Tasks**.

- Routers
- Services
- Schemas
- Business Logic
- Validation

Business logic belongs only inside the service layer.

Routers should remain thin.

---

## Endpoints (Phase 1: Tasks)

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/me` | Return current authenticated profile and workspace |
| GET | `/api/tasks?workspaceId=` | List all tasks for the workspace |
| POST | `/api/tasks` | Create a task |
| PATCH | `/api/tasks/{id}` | Update a task |
| PATCH | `/api/tasks/{id}/toggle` | Toggle task completion |
| DELETE | `/api/tasks/{id}` | Delete a task |

---

## Authentication

All endpoints (except `/health`) require:

Authorization: Bearer <token>

The authenticated user must only access data belonging to their own workspace.

---

## Validation

Perform all validation inside the backend.

Examples:

- Required fields
- Field length
- Enum validation
- Foreign key validation
- Workspace ownership
- Permission checks
- Duplicate detection
- Business rules

The frontend must never implement business logic.

---

## API Responses

Return proper HTTP status codes.

- 200 OK
- 201 Created
- 204 No Content
- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
- 409 Conflict

---

## Important

The Supabase database schema is the **single source of truth**.

Every API endpoint, Pydantic schema, service, validation rule, and query must match the database exactly.

Do not create fields or relationships that do not already exist in Supabase.

Implement the backend around the existing database, not the other way around.
